# BT-CEP 自适应过期堆压缩：阶段性研究成果与复现记录

日期：2026-10-08
代码基线：`fab31d8`（新增研究代码尚未提交）
本报告记录第六阶段结束后的正确性修复、复测和复现环境。历史 CSV 均保留，所有本轮结果使用此前未占用的文件名。

## 1. 研究问题与范围

BT-CEP 为事件序列匹配维护每个用户的活动实例。Expiration-indexed 管理器用字典按用户定位活动实例，并用 Min-Heap 按截止时间全局清理；实例成功完成时，堆中的对应条目不会立即删除，因此会留下失效记录。长期运行时，这些记录可能远多于活动实例。

本研究检验两件事：自适应压缩能否在不改变匹配结果和过期语义的前提下控制堆记录；其运行时间、重建开销和内存变化如何。默认规则为 `H > max(64, 2*A)`，候选规则为 `H > max(128, 3*A)`，其中 H 是堆记录数、A 是活动实例数。

本报告把证据分成三类：

- **实测事实**：自动化测试断言或本次 CSV 直接记录的结果。
- **推断**：根据实现和测量提出的解释，仍受工作负载及测量方法限制。
- **未验证假设**：当前 PoC 未覆盖，不能当作已有结论。

## 2. 算法方案与开销

| 管理器 | 活动实例组织 | 过期处理 | 主要代价（N 为每事件检查的实例数，A 为活动实例，H 为堆记录） |
|---|---|---|---|
| Baseline | 按用户扫描实例集合 | 每事件扫描活动实例 | 普通事件约 O(A)；状态 O(A) |
| Context-indexed | 用户字典 | 每事件仍需扫描活动实例找过期项 | 用户路由平均 O(1)，过期扫描 O(A)；状态 O(A) |
| Expiration-indexed | 用户字典 + Min-Heap | 只弹出截止时间早于当前事件的堆顶项 | 建/弹堆记录 O(log H)，弹出 K 条为 O(K log H)；状态 O(A+H) |
| Compact-expiration | 同上，超过阈值后重建有效堆 | 触发时从活动实例重建并 heapify | 常规堆操作 O(log H)；单次压缩 O(A)，额外摊销成本由触发频率决定；状态 O(A+H) |
| Optimized Compact-expiration | 同 Compact，减少安全条件下的重复阈值检查 | 相同过期和重建语义 | 检查次数减少，但单次压缩仍为 O(A)；状态 O(A+H) |

基于阈值规则，压缩检查后 H 满足 `H <= max(M, c*A)`。新建记录和删除活动实例等状态变化之间，界限只能按操作完成时判断；本实现的测试在每个处理事件后检查。无压缩时没有此上界。堆记录数是数据结构状态指标，不等同于实际字节数。

## 3. 正确性审查与修复

### 3.1 已修复缺陷

发现的边界情形是：已有 64 条失效记录时，新用户创建活动实例。创建过程先把新堆记录加入堆，随后阈值 `H > max(64, 2*A)` 成立，压缩发生在该实例第一次处理事件、根 Window 初始化 `start_time` 之前。若重建只从已初始化的 Window 状态推导截止时间，新实例会被错误排除，之后即使事件时间越过截止点也没有堆记录触发清理。

Compact 和 Optimized Compact 现在在创建实例时保存绝对截止时间 `instance.expire_at = event.timestamp + window_size`；压缩重建从该字段恢复活动实例的堆项。事件到达时仍由根 Window 判断是否超过窗口，堆负责到期候选的调度，当前字典实例 ID 再次校验后才允许删除。严格使用 `deadline < current_time` 弹出，故截止点本身仍有效。

### 3.2 当前证据

- **实测事实**：新增回归测试先制造 64 条失效记录，再创建尚未首次 tick 的新实例并触发压缩；验证其截止记录仍在堆中，且越过截止时间后实例会被清除。
- **实测事实**：截止点事件成功匹配；截止点之后的事件触发过期清理；跨用户事件可以触发全局过期。
- **实测事实**：旧堆项的 `instance_id` 与该用户当前活动实例 ID 不符时不会删除替代实例。同一用户重新创建使用新的实例 ID。
- **实测事实**：Compact、Optimized Compact 与原有管理器在自动化测试和本轮三方/阈值/长期流检查中检测序列和活动实例历史一致。
- **实测事实**：当前全套自动化测试 44 项通过。

### 3.3 Window 与时间边界

- 压缩管理器明确要求实例树根节点提供 `window_size`。Window 位于 Sequence 等非根节点时，管理器拒绝创建并报 `ValueError`；新增测试覆盖该拒绝路径。
- **未验证/不支持保证**：根 Window 内部再嵌套 Window 的组合没有纳入测试。根节点过期检查不会递归检查子 Window；`TreeInstance` 也只读取根节点的 `expired` 标志。因此不能声称嵌套 Window 的过期传播语义正确。后续应明确拒绝嵌套，或定义并实现递归过期策略，再补测试。
- **实测事实**：事件流实验按时间戳非递减构造，Window 边界包含截止点。
- **未验证假设**：Runtime 不强制事件时间非递减。乱序事件可能使堆顶截止顺序与事件处理时间关系复杂；当前研究只在单调事件时间假设下成立。
- 同一用户同一时刻依然遵循 Single-active 策略；活动实例存在时重复 start 不创建第二个并行实例。完成或过期移除后才可重建。上述单活跃语义由既有测试和重建回归场景覆盖。

## 5. 性能对照（修复后）

以下是 3,000 用户三方对照的吞吐量，单位为事件/秒，格式为均值 ± 样本标准差（每格 10 次）。

| 负载 | Expiration-indexed | Compact 默认 | Optimized Compact 默认 |
|---|---:|---:|---:|
| 大量活动、少量完成 | 307,878 ± 24,982 | 237,201 ± 11,398 | 266,783 ± 11,032 |
| 快速完成 | 363,619 ± 24,050 | 269,947 ± 8,205 | 304,742 ± 9,772 |
| 连续创建与过期 | 471,869 ± 32,059 | 380,984 ± 8,149 | 435,842 ± 11,855 |
| 高活动阈值压力 | 313,889 ± 10,489 | 230,789 ± 13,476 | 252,036 ± 14,435 |

高活动阈值压力下，未压缩 Expiration-indexed 的峰值/最终堆为 93,000；Compact 与 Optimized Compact 均压缩 27 次，峰值 H 为 9,000、最终 H 为 3,092。优化阈值检查版本比 Compact 默认版快约 9.2%，但吞吐仍低于 Expiration-indexed。快速完成负载中 Optimized 比 Compact 快约 12.9%，堆峰值均为 3,000，结束时均剩 45 条记录。

**推断**：此结果与“减少部分阈值检查可回收 Compact 的一部分额外开销”相符。它不证明所有差距都来自压缩：实现路径还包含状态计数、分支、不同的过期流程和 Python 调度成本。高活动压力计时循环包含每事件堆峰值采样，且 manager 有阈值检查计数器；它们会影响绝对值。尽管比较各策略使用同一采样循环，仍应把绝对吞吐视为该基准仪器下的结果。

## 6. 阈值消融与重建代价

3,000 用户高活动压力场景（183,000 个事件，每项 5 次）的阈值结果：

| 阈值策略 | 吞吐（事件/秒，均值 ± SD） | 压缩次数 | 峰值 H | 最终 H | 进程峰值工作集（MiB） |
|---|---:|---:|---:|---:|---:|
| 无压缩 | 238,745 ± 15,612 | 0 | 93,000 | 93,000 | 109.23 |
| `max(32,1.5A)` | 215,287 ± 9,755 | 45 | 7,103 | 3,156 | 109.23 |
| `max(64,2A)` | 224,347 ± 5,616 | 27 | 9,000 | 3,092 | 109.23 |
| `max(128,3A)` | 227,685 ± 5,673 | 14 | 12,000 | 3,000 | 109.23 |
| `max(256,4A)` | 221,149 ± 21,845 | 9 | 15,000 | 6,046 | 109.23 |

**实测事实**：更宽松的阈值在此场景下减少重建次数、允许更大的堆峰值；无压缩堆最大。进程峰值工作集在 5 次重复的汇总中相同到 0.01 MiB 精度，不能据此分辨 Manager 的内存差异。各策略检测结果和最终活动数匹配。

阈值报告中的 `compact_overhead_attribution_4.csv` 是单独插桩诊断：阈值检查计时包住重建，重建计时是其中子集；其它路径时间是总计时扣掉检查计时的粗略剩余量，计时器自身也有开销。该诊断不应与未插桩吞吐直接等同。重建操作每次需要遍历活动实例并 heapify，单次为 O(A)；**推断**累计代价取决于触发次数和触发时 A 的分布，不能仅从总事件数推导。

## 7. 长期堆状态与内存

长期事件流采用固定种子 20261008，主体事件时间集中在 t=0，交错包含重复 start、成功完成、同用户重复使用和部分未完成实例；尾部安排截止点匹配和 t=31 的跨用户过期触发。该设计有意延迟 watermark 推进，以累积失效记录。每个组合在独立 Python 进程中运行，避免前一个策略的 Python 堆分配影响下一个策略的进程峰值。

500,000 事件结果（每项 3 个进程，吞吐和标准差为均值 ± SD）：

| 策略 | 吞吐（事件/秒） | 峰值 H | 采样峰值失效记录 | 压缩次数 | 累计重建时间 | 峰值采样 Manager 对象图估算 | 进程峰值工作集增量 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Expiration-indexed | 41,569 ± 326 | 160,064 | 159,999 | 0 | 0 | 22.79 MiB | 64.98 MiB |
| Compact 无压缩 | 40,061 ± 450 | 160,064 | 159,999 | 0 | 0 | 22.79 MiB | 64.88 MiB |
| Compact 默认 | 170,740 ± 2,619 | 129 | 63 | 2,467 | 35.42 ms | 71.1 KiB | 0.775 MiB |
| Compact 候选 | 179,287 ± 5,600 | 193 | 126 | 1,242 | 19.69 ms | 80.3 KiB | 0.879 MiB |
| Optimized 默认 | 189,452 ± 2,809 | 129 | 63 | 2,467 | 34.11 ms | 71.1 KiB | 0.827 MiB |
| Optimized 候选 | 188,274 ± 4,438 | 193 | 126 | 1,242 | 20.80 ms | 80.3 KiB | 0.872 MiB |

重建累计时间随规模增长。以 Optimized 默认策略为例，10k、100k、500k 事件分别重建约 55、498、2,467 次，累计重建时间约 0.67、6.85、34.11 ms。候选阈值的重建次数和总时间较低，代价是峰值堆上界从 129 增到 193。累计重建耗时只计 `_rebuild_heap` 方法本身，不含每次触发前判断及外围调用。

**实测事实**：在该延迟 watermark 压力流中，无压缩峰值 H 随流规模约为 3,264、32,064、160,064；默认和候选阈值将峰值 H 控制在 129/193，且逐采样点检查 `H <= max(M,c*A)`。压缩组在尾部清理之后最终堆为 0。对象图估算和进程工作集增量都显示压缩组较小。

内存口径必须区分：对象图估算只遍历管理器的活动字典和堆可达的 Python 对象；工作集是 Windows 进程整体指标，包含解释器、导入、运行时和分配器行为。CSV 中 raw 的结束时对象图可能在尾部过期后很小；本报告使用 `peak_sampled_manager_state_bytes` 作为流中峰值状态，不把最终值冒充峰值。工作集增量是独立 worker 的峰值工作集减去处理前当前工作集，不等同于 Manager 实际分配量。

## 8. 结论：事实、推断与待验证问题

### 有直接实验支持

1. 新实例在首次 Window tick 前触发堆重建的缺陷已由回归测试复现并修复；重建现在使用预存的绝对截止时间。
2. 截止边界包含、跨用户过期、同用户替换实例的 ID 防护在当前被测根 Window / 单调时间条件下得到测试支持。
3. 三方对照、阈值消融、长期流的检测与活动实例状态检查通过；全套 44 项测试通过。
4. 延迟 watermark 的合成负载中，压缩控制了堆记录增长；更宽松阈值减少压缩次数并增大 H 上界。
5. 本轮独立进程实验观察到压缩组对象图估算和整个进程峰值工作集增量下降。

### 有数据但属于有限推断

1. 减少阈值检查可能解释了 Optimized 相对 Compact 的部分吞吐改善；本轮 3,000 用户场景中优化版仍慢于未压缩 Expiration-indexed。不能把全部差距归为压缩重建。
2. 压缩在有大量失效堆项积累的场景下可能提高总吞吐，因为堆操作不再面对持续增长的陈旧项；当前压力流刻意构造该条件，不能外推到一般实时流。
3. 长期内存收益在本轮合成压力流中可观测，但真实生产流能否复现仍未知。

### 未验证假设与边界

- 嵌套 Window 的递归过期语义、乱序事件时间、动态窗口长度和非 Window 根节点不在当前支持保证内。
- 真实事件分布、生产 watermark、不同硬件/Python 构建和长期服务进程中的吞吐/内存效果未知。
- 当前长期实验每格仅 3 次；标准差小不代表跨环境稳定，也未做统计显著性检验。
- 阈值是否存在跨工作负载通用最优值、是否需要按 A/H 自适应选择，仍是研究假设。
